# DomainScan — текущий технический аудит

_Обновлено: 2026-08-20._

## Итог

Проект перешёл от демонстрационного MVP к проверяемой архитектуре расширения. Критические проблемы
жизненного цикла вкладок, границы сайта, неполной модели IP и независимого выпуска устранены.

Текущее состояние:

- 94 модульных и worker-теста;
- 10 сквозных сценариев с загрузкой расширения в Chromium;
- полный ICANN + PRIVATE Public Suffix List с воспроизводимой генерацией;
- единый конвейер `verify -> package -> release`;
- локальная модель сигналов окружения без внешних запросов и без сбора возвращаемых значений.

## Что исправлено

### Состояние вкладок

Панель перепривязывается при смене активной вкладки и восстанавливает соединение после остановки
Manifest V3 service worker. У каждой вкладки отдельное состояние и отдельная запись
`chrome.storage.session`.

История сохраняется при переходах по путям и любым поддоменам одного регистрируемого домена.
Переход на другой регистрируемый домен очищает только сведения предыдущего сайта в этой вкладке.
Пауза не мешает обработать сам переход, поэтому старые сведения не показываются под новым адресом.

### Домены и IP

Регистрируемый домен определяется по полному PSL, включая частные, wildcard- и exception-правила.
Unicode-домены нормализуются в Punycode. IPv4/IPv6 строго проверяются и приводятся к устойчивому
виду.

Для узла хранится весь список замеченных IP, а не одно последнее значение. Поздний ответ от
предыдущего сайта не может обогатить новую сессию: ответ связывается с исходным request ID, вкладкой,
узлом и site key.

### Сигналы окружения

Инструментирование фиксирует только факт вызова разрешённого API:

- чтение Canvas;
- запрос производителя/рендерера WebGL;
- чтение данных аудиоанализатора;
- чтение часового пояса/смещения;
- чтение языков браузера;
- вызов геолокации;
- запрос подробных User-Agent Client Hints.

Обычный WebGL-рендеринг и загрузка JavaScript не считаются цифровым отпечатком. Один слабый признак
показывается как наблюдение окружения; несколько слабых или чувствительный признак — как возможный
сбор отпечатка; геолокация остаётся отдельным фактом. Результат API и реальные значения не
сохраняются, поэтому интерфейс не утверждает, что запрос был успешен.

### Поставка

`.gitignore` закрывает локальные настройки, секреты, зависимости, кэши, отчёты Playwright, сборки,
архивы и временные файлы. Базовое состояние проекта отдельно зафиксировано и отправлено в `main`.

CI ставит зависимости строго по lock-файлу, проверяет синтаксис, manifest/локали, PSL, Node-тесты и
сквозные Chromium-тесты. Архив создаётся после успешной проверки по строгому списку файлов,
проверяется через `unzip -t`, получает SHA-256 и передаётся в выпуск без повторного выполнения кода.

### Заметность инструментирования

Обертки над встроенными методами раскрывали себя: `Function.prototype.toString` возвращал исходник
обертки вместо `[native code]`, у обертки появлялось собственное свойство `prototype`, а в стеке
ошибок страницы был виден `chrome-extension://<id>/src/content/fingerprint-probe.js`. Защита Qrator
считала такой браузер подделанным и вместо решаемой проверки отдавала 403; заодно любой сайт мог
определить расширение по его ID.

Теперь обертка объявлена сокращенным методом, `toString` подменен один раз до первой обертки и
отдает исходник заменённой функции, а ошибки пробрасываются без кадров content script. Проверено
A/B-прогонами на `login.mts.ru`: 6 из 6 запусков до правки давали жесткий 403, после правки
поведение совпадает с браузером без расширения.

### Идентичность сайта

Сайт вкладки определялся по запрошенной навигации, а не по состоявшейся. Из-за этого скачивание файла
с другого домена подменяло заголовок панели и стирало улики текущего сайта, а при неизвестном сайте
(холодный старт service worker, обновление расширения при открытых вкладках) назначения одного сайта
показывались под другим. Проверено прогонами: до правки переход alpha -> beta оставлял в состоянии оба
хоста, а клик по ссылке на скачивание давал `pageHost=files.gamma.test` при пользователе на
`shop.alpha.test`.

Теперь идентичность берется из подтвержденного URL вкладки (`tabs.onUpdated`), при старте все открытые
вкладки засеваются через `tabs.query({})`, а улики, собранные при неизвестном сайте, отбрасываются, а
не приписываются новому. Запрос документа остается видимым назначением той сессии, из которой он был
сделан, поэтому скачивание не теряется. Новое разрешение не понадобилось: URL вкладки доступен по
уже выданным host permissions.

Сигнал окружения привязывается к сайту по documentId, а при его отсутствии по верхнему URL вкладки, а
сообщение, которое не удается привязать, отбрасывается. Значение `pageHost`, читавшееся внутри страницы, из протокола
убрано.

Панель показывает, с какого момента ведется запись по текущему сайту, потому что часть запросов первых
секунд сессии Chrome не отдает расширению вовсе.

### Обновление списка

Список перестраивался целиком на каждое сообщение STATE, то есть на каждый запрос страницы: раскрытый
блок resolved IP захлопывался, а фокус клавиатуры уходил из списка в body. На живой странице с потоком
запросов адреса было фактически не рассмотреть.

Теперь строки сверяются по ключу: назначение сохраняет свой элемент, пока остается видимым, а части
строки перерисовываются только при изменении собственного содержимого. Оба свойства закреплены
сквозными тестами, которые падают на прежней реализации.

### Стоимость накопления

Состояние вкладки целиком писалось в `storage.session` и отправлялось в панель на каждое событие. На
профиле 2000 запросов к 300 узлам это 4000 записей и 611 МБ сериализации при итоговом состоянии 218 КБ;
чистое время обработки в Node — 3957 мс.

Теперь накопление доставляется пачками: событие помечает вкладку, а запись и отправка происходят раз в
100 мс, тогда как подтвержденная навигация и команды панели уходят немедленно. На том же профиле — 11
записей и 1,6 МБ, время 285 мс, итоговое состояние идентично. Закрытая вкладка удаляется из очереди
доставки, поэтому отложенное обновление не может ее воскресить; это закреплено тестом.

Панель, кроме того, выводила строки дважды за перерисовку и сортировала все назначения только чтобы
показать их число — теперь набор строк выводится один раз за отрисовку.

### Правки по внешнему ревью 0.3.0 и 0.3.1

Ревью нашло дефект в самом источнике идентичности: `commitNavigation` вызывался на любое событие
`tabs.onUpdated`, включая смену заголовка и значка, и такое событие с прежним URL съедало ожидаемую
навигацию. Сценарий массовый: страница тикает заголовком, пользователь уходит на небыстрый сайт, и
улики нового сайта теряются. Проверено прогоном на живом браузере — до правки resolved IP документа
нового сайта терялся, а в чистой сборке без запроса favicon пропадало и само назначение.

Исправлено: коммитом считается только сообщенная смена URL, а также завершенная загрузка документа,
который в этой вкладке уже запрашивали (иначе reload не переустанавливал документ); ожидаемая
навигация принадлежит одному хосту и консумируется только коммитом этого хоста; отдельный выход по
совпадению URL убран, потому что именно он оставлял устаревший documentId при возврате из bfcache.
Сигнал от документа со статусом не `active` отбрасывается, поэтому улика из bfcache-документа не
приписывается новому сайту. Вкладка, ушедшая на не-web адрес, теряет сайт и улики вместо показа
прежнего сайта как текущего.

Замечание о 12-часовом формате времени у русской локали проверено и отклонено: в расширении язык
документа ставится из `chrome.i18n.getUILanguage()` до первой отрисовки и дает 24-часовой формат;
12-часовой возникал только в демо-режиме, где `chrome.i18n` отсутствует, и это поправлено отдельно.

## Оставшиеся платформенные ограничения

Это не дефекты текущей реализации:

1. Chrome не всегда сообщает IP для кэшированных ответов и отдельных транспортных путей.
2. `webRequest` видит только открытие WebSocket, но не содержимое сообщений.
3. Сигнал API доказывает вызов, но не намерение страницы и не полезность полученного значения.
   Страница может намеренно вызвать API, не используя результат.
4. `<all_urls>` нужен для наблюдения произвольных назначений и инструментирования страниц; это
   широкое разрешение необходимо ясно объяснить при публикации в Chrome Web Store.

## Рекомендованные следующие дополнения

1. Перед публикацией подготовить политику конфиденциальности и понятное обоснование `<all_urls>`.
2. Добавить проверку установленного ZIP в Chrome как отдельный выпускной smoke-тест, если формат
   магазина станет частью процесса.
3. Добавить лимиты/свёртку для очень длинных историй одного сайта, не удаляя исходные данные
   бесшумно.
4. Провести отдельный аудит доступности экранным диктором в Chrome на Windows и macOS.
5. Настроить защиту ветки `main`, требующую успешную задачу `Verify` перед слиянием.

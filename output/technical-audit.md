# DomainScan — Технический аудит готовности

_Дата аудита: 2026-07-18. Платформенные факты повторно сверены с актуальной документацией Chrome for Developers через Context7._

## 1. Резюме

Проект находится в стадии **продуктово-дизайнерской разведки**. **Кода расширения не существует**: в репозитории нет `manifest.json`, service worker, кода боковой панели, `package.json`, а также какого-либо build/lint/test-инструментария. Всё, что есть, — это продуктовая документация, спецификация UI, шесть статичных HTML-макетов и их скриншоты.

Вывод по готовности: **0% готовности к production**. Есть прочная продуктовая и дизайн-основа, но реализация не начата. Хорошая новость — платформенные факты (`product-facts.md`) актуальны и подтверждены, так что можно переходить к разработке без риска строить на устаревших API.

## 3. Актуальность платформенных фактов (сверено 2026-07-18)

| Утверждение из `product-facts.md` | Статус | Комментарий |
|---|---|---|
| Только Manifest V3, фоновый контекст — event-driven service worker | ✅ Подтверждено | — |
| `chrome.webRequest` доступен в MV3 для наблюдения/анализа (неблокирующий) | ✅ Подтверждено | `webRequestBlocking` доступен только policy-installed расширениям; обычный `webRequest` для наблюдения работает |
| `webRequest` видит handshake WebSocket, но не сообщения | ✅ Подтверждено | Соответствует задокументированной области действия API |
| Side Panel API + `setPanelBehavior({ openPanelOnActionClick: true })` | ✅ Подтверждено | — |
| Панель может быть привязана к конкретной вкладке | ✅ Подтверждено | Через `sidePanel.setOptions({ tabId, … })` и `tabs.onActivated` |

**Новый важный нюанс, которого нет в `product-facts.md`** (из текущей документации webRequest):

- Чтобы наблюдать sub-resource-запрос, расширению нужен доступ **и к URL запроса, и к его инициатору**. На практике для наблюдения за *всеми* назначениями произвольного сайта потребуется широкое host-разрешение (`<all_urls>`). Это прямое следствие для приватности и для ревью в Chrome Web Store — нужно заранее продумать формулировки разрешений.
- `chrome.sidePanel.open()` можно вызвать **только в ответ на действие пользователя** (жест). Для «клик по иконке открывает панель» это закрывается `openPanelOnActionClick`.
- **Fingerprinting не виден через `webRequest`.** Обращения к Canvas / WebGL / audio / device API — это не сетевые запросы. Эвристика «возможен fingerprinting» из макетов требует **отдельного content-script с инструментированием страницы** и явного раскрытия этого факта пользователю. Это архитектурный пробел, который нужно учесть.

## 4. Оценка технической готовности (что нужно построить)

Ни один из компонентов ниже не существует:

- **`manifest.json` (MV3)** — ключи `action`, `side_panel`, `permissions: ["webRequest", "tabs", "storage"]`, `host_permissions: ["<all_urls>"]`.
- **Service worker** — слушатели `webRequest` (`onBeforeRequest`, `onResponseStarted` — здесь доступен реальный IP через поле `ip`), захват handshake WebSocket (`ws://` / `wss://`), накопление по вкладкам, дедупликация.
- **UI боковой панели** — HTML/CSS/JS выбранной концепции, связанный с реальными данными через message passing / `chrome.storage`.
- **Модель данных + трансформации отображения** — режимы «точные хосты / свернуть поддомены / регистрируемые домены». Режим регистрируемого домена требует **Public Suffix List** (данные нужно упаковать в расширение).
- **Персистентность состояния** — service worker эфемерен; накопление должно переживать перезапуски (через `chrome.storage.session`).
- **Content-script для эвристики fingerprinting** + честное раскрытие инструментирования.
- **Локализация** — `_locales` для EN/RU (по локали браузера, согласно `PRODUCT.md`).
- **Копирование** — `navigator.clipboard` в контексте панели; раздельные цели (домены / IP / выбранное).
- **Инструментарий сборки и тестов** — отсутствует полностью.

## 5. Ключевые риски и решения до начала кодирования

1. **Широта host-разрешений** (`<all_urls>`) — влияет на ревью в Web Store и на доверие. Нужна прозрачная коммуникация приватности (продукт как раз про это).
2. **Жизненный цикл service worker** — накопление обязано переживать выгрузку SW; нельзя держать данные только в памяти.
3. **Режим регистрируемого домена** — нужен Public Suffix List (без него «свернуть до домена» будет некорректным для доменов вроде `co.uk`).
4. **Захват IP** — поле `ip` надёжно только в `onResponseStarted`; кэшированные и часть HTTP/3-ответов могут не давать IP. UI должен корректно обрабатывать отсутствие IP.
5. **Fingerprinting — только эвристика** — требует инструментирования страницы (content script), и формулировки в UI никогда не должны заявлять достоверность.
6. **Нет автоматических тестов** — для расширения полезны юнит-тесты на трансформации (свёртка доменов, PSL) и хотя бы ручной чек-лист для сценариев панели.

## 6. Рекомендованная последовательность работ (MVP → v1)

1. Скелет: `manifest.json` + service worker + захват через `webRequest` + пустая боковая панель, открываемая по клику на иконку.
2. Накопление по вкладкам + `chrome.storage.session` (переживает перезапуск SW).
3. Подключение **выбранной дизайн-концепции** к реальным данным.
4. Трансформации отображения (точные / свёртка / регистрируемые + Public Suffix List).
5. Раздельные действия копирования (домены / IP / выбранное).
6. Эвристика fingerprinting (content script + раскрытие).
7. Локализация EN/RU.
8. Тесты + упаковка для Web Store.
